# 业务定制如何接入 DSH

**结论**：有接口就用接口；接口不够、或缺一项通用能力时直接改 DSH 源码；DSH 源码随子模块带着，改起来顺手。唯一的红线是**业务逻辑（heronAi、common、fl、host 的产品名、品牌、策略）不进 DSH 源码**。

| 优先级 | 做法 | 适用情形 | 代码放哪 |
| --- | --- | --- | --- |
| 1 | 原生扩展点 | DSH 已有插槽、服务、注册接口、配置项或样式锚点 | 业务包（common / heronAi / host），只做加法 |
| 2 | 改 DSH 源码 | 没有可用接口、需要修 DSH 自身的问题，或缺一项任何 DSH 应用都用得上的通用功能（如多目录工作区） | `packages/dsh` 子模块里的提交，只放通用口子、通用修复或通用功能；业务包再通过口子做加法 |

改 DSH 源码的纪律：

1. **不含业务**。提交里不出现产品名、品牌、产品专用配置或业务分支；放到官方仓库也说得通。
2. **一事一提交**。每个提交只做一个口子、一个修复或一项功能（功能可拆成几个依次提交），提交说明写清用途，保持简短：标题加几行要点，不附 `Upstream-PR` 尾注。
3. **只改必须改的**。能加一个配置项、插槽或注册接口就不改内部流程；不顺手重构、不改无关文件。通用功能按 DSH 自身规范实现，测试与包文档随提交更新，并在 DSH 仓内跑对应测试。
4. **官方合入即删**。升级子模块时，上游已提供的口子丢弃本地提交，业务包改用官方接口；补丁只减不增是升级可控的前提。

补丁提交保存在 GitHub fork `github.com/ornithologist-love/deepseek-harness`，子模块从该仓库取；官方仓库只读，分支模型见 [Git 工作流](../guides/git-workflow.md#dsh-分支模型)。构建由 `scripts/dsh-patches.mjs` 找出补丁改动的官方包，`scripts/dsh-build/build.mjs` 只把这些包从源码编译后原位覆盖官方产物，其余包继续用官方预编译产物；拆成 host/client 两面编译配置的包按各自的叶子配置分别编译；自带 `tsdown.config.ts` 的 Host 包按该配置打出全部入口（包括 CJS worker）。静态库（`tsdown.config.ts` 调用 `staticLinked` 的包，如 `ui-primitives`）链接进预编译的 Web 壳 `apps/web`，单独重编不会进浏览器；补丁一旦改到静态库，构建改用 `apps/web` 自带的 Vite 和官方公开环境重建 Web 壳，其余第三方依赖可能比官方产物多出补丁版本差异。

现状：子模块为官方 `dsh-v0.2.2-rc.1` 加若干源码口子与修复（预设隐藏/锁定、按文档隐藏侧栏、按分区打开设置、目录对话框以发起窗口为 owner、MCP 大图片 base64 校验、模型设置页的部署配置与凭据提示插槽、交付文件预览插槽、聊天正文图片插槽与 `file:` 图片地址修复、菜单分组图标、模型菜单的图标/徽标/提供方配置插槽与推荐筛选，以及多目录工作区：工作区成员目录与草稿会话头登记、沙盒多根策略、各平台多目录执行与 Windows 成员集合写身份；会话延迟激活与会话命令中间件、模型目录展示元数据；权限选择的颜色、完全权限确认记忆与按预设隐藏，预设选择的按前缀隐藏与开发者工具门控；工作区展示（图标、置顶、"最近"分组、编辑入口、会话筛选、新会话直接新建）与启动不恢复主视图；会话区的品牌标题显隐、未归属会话的工作区标签、hero 工作区图标插槽、输入框工具行排布插槽、发送前等待与排队消息编辑投影；文件搜索的项目范围：排除目录与 `search_scope`，Heron.AI 用它跳过 UE 生成目录；插件管理的 `protectedBundles`，Heron.AI 用它把产品层 `@heron-ai/dsh-profile` 设为只读）。原侵入改动已全部改为原生扩展点、"源码口子 + 加法插件"、直接进 DSH 的通用功能或社区子模块改动，薄替换包均已删除（见下文"薄替换"）。

## 原因

Web 壳的缓存边界采用 Vite 实际读取的模块、样式、资源、Worker 和解析清单，并覆盖入口、公共资源、构建配置及依赖版本。前后端经常联动修改，按包名或目录划分会漏掉共享代码和生成接口；把所有补丁包产物都纳入又会让纯后端变化触发 Web 重打包。因此，依赖与产物完整性共同决定缓存是否可复用，输入记录缺失时重新构建。

DSH 是"一切皆插件"的底座，业务落在扩展机制上才能与底座升级解耦、归属清楚。早先的问题不是改了 DSH 源码，而是业务逻辑直接写进 DSH、散在各处，升级时分不清哪些是通用修复、哪些是业务，只能逐条重放。红线因此只针对业务。

通用功能也属于底座：会话控制、工作区、沙箱这类能力上游尚未实现时（如多目录工作区、会话延迟激活），放在业务包里只能整份替换官方实现；直接做进 DSH，改动集中在真实位置，也能原样提给上游。判断标准与口子相同：放到官方仓库也说得通，不出现产品名与产品策略。

DSH 尚在预发布阶段，很多位置没有扩展点。曾把"DSH 一行不改"当成绝对规则，改动并没有消失：原本几行的改动变成整文件复制，外加停用官方插件、插入替换包、迁移设置命名空间等接线；24 个替换包复制约 2.8 万行，真正改动约 4.4k 行，替换接线还引入过运行时回归（目录选择器的"添加工作区"按钮消失）。上游改动被复制的文件时，副本与补丁面对同样的冲突，只是合并工具从 git 换成了自写脚本。直接改源码的冲突只发生在改过的几行，审阅看到的也是真实改动。

两个原生机制限制决定了"全靠插槽"走不通：

- **插槽只能遮蔽，不能包装**。同一单元的低优先级注册会整个取代原组件，没有"渲染原件再加一点"的方式；只有 `kind: 'chain'` 的插槽能把控制权交给下一个。遮蔽一个大组件等于重写它。
- **语言包不能叠加**。`locale.register` 对同一命名空间的同一语言只接受一次，重复注册直接抛错（`packages/client/locale`），只改几句文案也做不成加法。

被否掉的做法：

| 做法 | 否掉的原因 |
| --- | --- |
| 在 DSH 源码里写业务逻辑 | 业务混进底座，归属不清，升级要逐条重放 |
| 构建后改写 DSH 产物 | 改动不在源码里，审阅和追溯都看不到 |
| 一律零改动、全部薄替换 | 改动换成整文件副本与替换接线，代码量和运行时风险更高，升级并不更省 |
| 用 DOM 选择器或样式覆盖内部类名 | 依赖内部结构，升级后静默失效 |

## 原生扩展点

已落地的例子：

- **暖玉 / 墨玉主题**用 `ThemeRuntime.register` 注册；外观设置行以更低 `priority` 注册到同一个 `settings.general.item` 单元覆盖原生行；选择存进 `heron-ai-theme-preference`，见 `packages/common/runtime/src/heron-ai/themes/client.js` 与 `palettes.mjs`。
- **退出诊断**由 common runtime 订阅 Cordis 的 `internal/status` 与卸载 promise，监听器独立存活到根卸载完成。`HERON_AI_EXIT_TRACE=1` 记录生命周期、产品自身的 EOF/迁移失败退出请求以及进程退出；其他原生退出请求只反映在生命周期和最终退出码中，不包装 `appExit`，不修改 Cordis/cmdline。

常用机制：插槽注册与同单元低优先级覆盖、cordis 服务、`webserver/index-inject` 启动注入、profile 的 `disabled` / `insert`、各插件的 `Config`。

## 薄替换

> 已全部退役（2026-10-25），不再新增。

曾经的做法：profile 停用官方插件，插入同位置的 `@common/<插件>` 包，只复制改动过的上游文件，其余模块经上游包的 `"./src/*"` 引用。24 个替换包已逐项迁出并删除，副本同步工具随之移除。

工具行排布插槽 `conversation.input.controls` 以 owner props 传递已渲染的控件，是 DSH “owner props 不放 ReactNode”规则的例外，已写进 ui-conversation README 的已知限制。取舍理由：UE 插件通过 `@common/toolbar` 的 `ToolbarItem` 声明自己的工具项与溢出优先级，工具栏必须留在 Heron.AI，而排布它需要控件元素本身。

Typert 的 CSS、字体和文本资源过滤放在 `scripts/dsh-build/typert.mjs`。它通过官方 `WorkspaceCaches` 取得清单快照，仅过滤内存中的资源导出，再交回官方分析器；不改写安装包清单、生成器源码或编译产物。

## 社区子模块

三个社区插件分别为 `packages/community/dsh-mcp-manager`、`packages/community/dsh-skill-manager` 与 `packages/community/dsh-better-sidebar`。前两个是放在 GitHub 的公开 fork，提交不得含业务专有内容或私有信息，规则比 DSH 宽：**可以直接改源码，不要求提上游**。产品需要的行为直接改在 fork 里，不追社区仓自己的测试与覆盖率规范；fork 按自有代码维护。保留一条习惯：产品名与产品专用取值不硬编码，经插件配置或注册接口传入，业务包负责提供。

BSB 自 2026-11-07 起直接固定官方 Tag，不维护 fork、不改源码：官方 v0.30 已适配 DSH 0.2.2，原有补丁只剩设置页外观一项，不值得长期追一个每周发版的上游。需要的修改提 PR 给官方。官方包不带 fork 标记，Heron.AI 构建按 `forks.json` 的版本与官方提交识别它，并在编译前运行 `prepareScripts` 声明的生成步骤（如 mermaid 内联资源）。详见 [Git 工作流](../guides/git-workflow.md#bsb-官方版本)。

MCP 与技能管理器按自有 fork 维护，不要求与社区上游保持可合并；BSB 直接用官方版本。三者都从子模块源码编译，改源码不增加薄替换层；社区更新由我们决定是否同步，冲突在对应源码分支解决。

## 测试与覆盖率

覆盖率只说明测试运行时每一行、每个分支、每个函数至少执行过一次，不说明结果正确：没有断言的调用也算覆盖；代码里压根没写的必要检查不产生分支，覆盖率照样满；分支各走一遍不代表并发、时序与配置组合都试过；为凑覆盖率补的测试常常只是把当前实现抄成断言。它也与运行性能无关，最后几个百分点多是防御分支，补齐成本高、收益低。

因此 DSH 补丁的验收以行为为准：测试断言用户可见的结果（角色、名称、文本、Remote 结果），新配置的默认值保持现有行为，宿主可见行为在真实宿主里验证。覆盖率在提交前看一次，只确认新增和修改的行都被执行到，不在开发循环里追 100%。

DSH 上游 CI 要求 `packages/*/*/src` 按文件 100%（见 `packages/dsh/docs/testing.md`），这是上游的门槛设计：规则不会被个例逐步放松，并迫使走不到的分支要么删除、要么以 `/* v8 ignore -- 理由 */` 显式说明。这条只在补丁提交上游前补齐；本地开发与 Heron.AI 出包不以它为门槛，社区子模块不要求。

## 提交上游

源码口子的形态与提给 DSH 官方的 PR 一致，本地提交与 PR 同步维护。上游接受后，子模块升级到含该口子的官方版本并丢弃本地提交；上游不接受的通用口子可长期保留在公开 fork，提交说明写明理由。是否提交上游、何时提交由仓库维护者决定。
