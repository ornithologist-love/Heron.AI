# Heron.AI 架构

本文说明产品的运行形态、装配、数据与跨仓边界。业务和公共组件的分工见 [扩展架构](extensions.md)，协议细节见 [宿主契约](HOST-INTEGRATION.md)。

## 1. 运行形态

```text
宿主（App / WebView2 / 浏览器）
   │ 启动进程 + 承载 URL + 管生命周期
┌──▼─────────────────────────────────────────┐
│ AiHost（Node）                              │
│   DSH 底座（官方固定版本）                    │
│   Heron.AI 补充层（heron-ai/）                     │
└──┬─────────────────────────────────────────┘
   │ HTTP 127.0.0.1:<随机端口>（带认证 query）
┌──▼─────────────────────────────────────────┐
│ Web 前端：DSH 官方前端 + Heron.AI 组件           │
└────────────────────────────────────────────┘
```

DSH 持有应用、会话与工具循环，Heron.AI 在其上补充产品装配、模型和界面。DSH 子模块为官方提交加不含业务的通用口子、修复与通用功能；业务行为由产品包承载（见 [业务定制如何接入 DSH](dsh-customization.md)），官方产物内容不做改写。`forks.json` 只登记产品及社区包的构建。日常构建消费官方 npm 预编译包，具体固定与准备规则见 [依赖来源](../guides/dependencies.md)。

## 2. 启动与组合

### 本机启动

启动链路是 `main.mjs → prepareHeron.AI → prepareComposition → launchDsh`。组合复用静态模块，每次启动再注入实例配置：

1. 启动参数按宿主契约校验，未知参数会报错。
2. `DSH_VERSION` 与已安装版本精确匹配，升级时同步更新常量、`upstreams.json` 和 lockfile。
3. 组合缓存按内容哈希分目录，覆盖产品代码和依赖指纹，`content/` 则由运行时读取。
4. `composition.json` 保存可复用的模块组合，token、端口和 ready 路径放在本次进程的 include 中。

## 3. 补充层职责

补充层持有模型渠道、工作区、模板与产品设置，通过 `heron-ai/index.mjs` 统一装配。业务扩展提供内容，宿主提供运行事实，组合层据此生成当前产品。

模型目录与执行适配分开：目录描述可选模型与能力，客户端管理本地凭据、偏好和原生路由；外部插件可以贡献目录和传输实现。公共版本没有预设的团队服务。配置与缓存规则见 [Provider 目录](../guides/provider-catalog.md)。

**模型执行**：会话使用 DSH 原生 Agent 循环、Skill 与 MCP。可选模型适配器只提供模型调用，不另造会话循环。模型能力以运行时目录和会话信息为准，不按模型名称推断。

**插件生命周期由 DSH 管理**：DSH 负责 Agent／工具调度、取消、会话持久化和插件树销毁。扩展通过 `ctx.plugin()`、`ctx.on()`、`ctx.effect()` 登记子插件、订阅与资源，由 owner context 统一撤销；`appReady` 提交后向宿主报告就绪。普通退出使用 stdin EOF（[H4](HOST-INTEGRATION.md#h4-退出协议)）。用户数据独立于运行资源保留。

## 4. 数据：载荷只读，状态全在 stateDir

| 位置 | 内容 |
| --- | --- |
| `<stateDir>/dsh/` | DSH home：profile、会话、凭据 |
| `<stateDir>/dsh/session-configurations` | **草稿**配置（模板/模型/权限/工作区） |
| `<stateDir>/runtime/modules-<key>/` | 组合缓存 |
| `<stateDir>/content/` | 部署后的技能与模板 |
| 集成包指定的私有位置 | 外部身份与部署凭据（**不得提交**） |

草稿配置与正式 Session 日志分别存储，发送消息时才把配置事件写进正式日志。

**旧版配置迁移**：旧 `.heronAi` 数据根的对话导入已移除，早先导入的会话就是普通 DSH 会话。`migration/config.mjs` 仍在首次启动时把旧 Skills、MCP 与 OAuth 凭据迁入，并在没有 `mcp-servers.json` 时用随包列表播种，记录在 `<stateDir>/dsh/migration/heron-ai-v1/`。原始文件只读不删；同名冲突另存为 `-legacy-<hash>`，不覆盖用户当前配置；完成标记写入后不再重扫旧数据。

**受管 MCP 默认项**：可选内容来源可以贡献连接配置，更新仅作用于仍由来源管理的项，保留用户启停选择和个人配置。公共版本不包含团队服务器地址或凭据。

数据目录与用户工程分别管理。启动时会撤下历史版本误登记的数据目录工作区，保留对应的聊天记录和文件。

## 5. 新功能的归属

公共机制由运行时持有：模型与原生 Agent、模板和技能注册、MCP 生命周期、工作区与宿主协议。业务编排、业务 Skill、远程服务策略、自动化请求与产品更新由可选包贡献。命名入口和宿主提供者的装配边界见[扩展架构](extensions.md)。

## 6. 构建与发行

构建把源码和依赖组装为独立载荷，输出目录与输入分开；`mirror` 只写已校验的输出范围，发行载荷以真实文件交付。

Node 载荷记录组件输入和输出内容摘要，Git 只提供源码文件清单，实际字节决定复用，包含未提交文件。载荷覆盖产品、实际编译的 DSH／社区源码、构建脚本与锁文件。生成目录及依赖安装目录不进入源码清单，输出目录仍校验真实内容。回执只在成功且输入未发生变化时提交，存于 `.cache/components/`。

外部插件只有在构建时显式指定后才进入载荷，缺少必需输入直接失败。插件包装分别校验适配器与 Node 载荷，Debug 包携带对应 PDB。

依赖装配先解析完整的包位置与版本，再使用与发行裁剪共用的文件规则筛掉开发文件；源码包及已安装依赖只读。每个保留文件都记录输入与最终输出哈希，构建时校验真实载荷，只复制新增、缺失或内容变化的文件，并清理已移除的文件与包。父包更新保留其嵌套 `node_modules`，避免破坏并存版本；包清单中的本地版本与排除规则在写入前完成归一化。提交号等元数据变化只同步对应文件，不清空整个依赖树。

详细同步记录按输出目录存入 `.cache/dependency-assembly/`，不随产品交付；载荷中的 `.heron-ai-assembly.json` 只保留组合缓存需要的内容指纹。发行阶段对官方组合 YAML 的过滤会登记最终输出哈希，下次构建按过滤后的字节校验，避免反复恢复再裁剪。拷贝、裁剪和分发规则的内容均参与策略指纹，策略变化会重新核对文件集合。装配日志分别记录依赖图解析、指纹计算、同步、锁文件写入耗时及实际写入数量。

公共构建输出 `dist/app/AiHost`，独立 App 与外部宿主共同消费它。具体宿主包装由接入方交付。发布通过 `plan/build/verify` 三段校验；协议兼容范围由 `tools/release/protocol/` 维护。

## 7. 本地环境与验证

产品当前面向 Windows x64，Node 版本固定在 `node-runtime.json`。本地依赖通过 junction 复用，开发机器需要相应权限。验证使用标准构建、`verify-payload` 与受影响宿主的实际渲染；具体命令见 AGENTS。

## 8. 宿主与可选集成边界

公共 Facade 管理进程、WebView、就绪回执、退出和通用宿主控制。具体宿主适配器由接入方维护，可以通过自己的 SDK 编译和包装，再消费公共运行时；公共 App 不依赖某个宿主、服务器或产品更新系统。

远程登录、机器登记、中继、服务器常驻与更新策略属于提供相应能力的插件及服务端。它们与本地运行时分别交付，通过同一份原生会话、工作区与权限协议协作。

## 9. 通用层、业务包与宿主包

四层：DSH 底座 → common（产品核心）→ 业务包与宿主包。业务包回答"给哪个团队用"，宿主包回答"被谁嵌着"；两者平级、互不引用，去掉它们产品仍可独立运行。

组件归属、消费方、工作区数据流与稳定标识统一写在 [扩展架构](extensions.md)。具体宿主独立维护自己的适配器，复用公共组件。

宿主实现由启用包的 `heron-ai.hostProfiles` 贡献，通用启动层验证和选择；`--config` 的 `aspects` 覆盖贡献者的默认业务标签。契约在 [HOST-INTEGRATION](HOST-INTEGRATION.md) H2.2、H5.1。

Persona / preset 同样按机制与内容分工：公共基底使用 DSH 原生预设系统，各业务贡献角色和组合。

项目源目录配置由产品通用层持有，通过底座 `sandboxPolicy.registerWorkspaceRoots()` 参与权限解析，通过 `workspaceRegistry.registerDirectories()` 决定新会话主要目录和成员归属。底座不依赖宿主或业务包；原生工作区身份与 Session 格式保持不变。使用规则见 [多目录工作区](../guides/multi-folder-workspaces.md)。
